# 条目内容格式：讨论记录（2026-10-16 → 10-19）

**结论：先按现有简洁格式试用，暂不改。** 已上线的只有一项：`search` 结果带一行 `summary`
（cb152eb，只展示不进索引，两道门禁不变）。

## 起因（一线 agent 研发反馈）

- agent 用编目做两件事：故障分析定位、故障预防（正向扫读代码）。
- 搜到条目后信息太少，仍要自己去 GitHub 查，相比直接搜 GitHub 效率提升有限，且短而抽象的条目容易让 agent 先入为主。
- 希望一条故障模式从头到尾闭环（现象 → 条件 → 确认与排除 → 根因 → 修复/规避 → 验证），叙述在前、像摘要。

## 结构上的三个原因

1. 编目最初是覆盖索引卡（服务检测器研究），细节留在链接里——对当时的用途，短是对的。
2. 扫描在 issue 刚提出时写入（常为 0 评论）。
3. `original` 只能经 `update --note` 追加，`--set original.*` 被禁止——回访查到的东西写不回正文。

另：迁移条目最密的描述常在 `original.meta`（旧 Markdown 标题下那行），推理库 571 条 meta 比 mechanism 还长，
而 `meta` 既不进嵌入也不进 BM25。

## 重提时的现成方案（未采纳，备查）

- **存储不动，给 agent 渲染 Markdown 视图**（`views/entries/<ID>.md`：导语在前、按节排、不含审计历史），
  而不是把存储改成原生 MD。
- **`original` 保持不可改（审计真源），另设可修订的叙述正文**，回访补全写入后者。
- **回访补全**：拉 issue 讨论 + 关联 PR + 改动文件，按节重写正文，保留报错原文与修复 diff 摘录；
  抗 bias：已证实/推测分写、可证伪的判别条件、带截至日期的闭环状态。
- **按路径反查**（预防用途）：由合入 PR 的改动文件建「路径 → 条目」索引，确定性、零网关调用。
- **检索不跟着变长**：索引固定在导语/现象/条件子集，完整正文只供阅读。
- **验证**（一线 A/B 做不了时）：闭卷充分性测试（以合入 PR 为外部真值）+ 近邻诱导测试（bias 代理）。
- 成本：试点 20 条约 300 次网关调用；全量粗估约 5000 次调用、数千万 token（未实测）。
