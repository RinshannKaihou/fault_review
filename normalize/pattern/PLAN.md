## 嵌入相似度：可当候选生成器，**不能**当判定阈值

| 测量 | 结果 |
|---|---|
| var 关系对的余弦 | 中位 **0.718**，p10 0.638，p90 0.788 |
| 随机对的余弦 | 中位 0.566，p90 0.632，p99 0.703 |

`cos ≥ 0.80` 的条目对共 134 对（10-14 估的 103 对已随编目增长），其中 57 对两端都已在家族里，
**77 对至少一端是孤立条目**——这是精度最高的一批扩展候选。

## 修订后的 B：三步，前两步成本很低

### 第 1 步：把现有森林固化成模式层

`build_patterns.py preview` 已离线推导完成（未写上游）。实测结果修正了两处原先的估计：

**(a) 模式标题必须生成，不能借用代表条目的标题（原估「~0 调用」是错的）**

`PAT-0113` 的代表标题是「vLLM Kimi-K3 parser 终止符假设不全丢 tool call」，但这个模式有
16 个成员（vllm 12 / sglang 4），涵盖 tool 数组非 object 项、`tool_choice=none`、
Qwen3 XML 参数正则过宽等不同解析器。代表标题带着实例的特指，直接当模式名会把整族窄化。

所以 199 个模式的 `title` 与 `shared_mechanism` 需要按成员集生成：1 个便宜模型写 +
2 票复核 ≈ **600 次调用**。

**(b) 199 个里 150 个可直接采用，57 个要先复核**

森林用连通分量算，等于假设了 var 的**传递性**——而「A 是 B 的变体」「B 是 C 的变体」
并不保证 A 与 C 同族。实测链深：

| 最大链深 | 1 | 2 | 3 | 4 |
|---|---:|---:|---:|---:|
| 模式数 | **150** | 33 | 11 | 5 |

- **纯星形（深度 ≤1）150 个、覆盖 357 条**：不假设传递性，可直接采用。
- 深度 ≥3 或子系统一致度 <0.6 的共 **57 个、覆盖 256 条**：需先复核。
- 深度本身不等于漂移：`PAT-0028`、`PAT-0030` 深度 4 但子系统一致度 1.00。

**漂移确有实例**：`PAT-0102` 有 25 个成员、跨 9 个栈，代表标题是「FP8 KV cache 量化误差
随上下文长度累积漂移」，但成员里有 radix 缓存跨序列污染、P/D connector 传空 KV、
Kimi-K3 跨请求上下文污染、PD 分离输出离题——它们共同点是「KV 内容被污染/错配」，
而不是代表标题说的那件事。这是链式拼接把两端无关的条目并进了一棵树。
`PAT-0102` 落在上面那 57 个里，说明这个筛选规则有效。

**其余成本仍在 schema 与工具改动**（不是算力）：两个编目仓库的 `catalog_tool.py` /
`SCHEMA.md` / `vocab.yaml` / `id_registry`（`PAT-` 命名空间）、`validate` 的成员双向一致校验、
views、RAG 的 parse 与检索投影、两份扫描说明。
**跨库模式为 0**（var 从不跨编目，跨库用 `cross`），所以两个编目各自一套 `PAT-` 编号即可，
不需要共享命名空间。

### 第 2 步：先把「同家族」的定义做出来（约 200 次调用）

这是 A 的教训直接转化的前置门槛，**不做这步就不要进第 3 步**：

1. 开放式归纳：对 30 对已接受的 var 关系，让模型描述「这两条共享什么」（不给定义），
   聚合这些描述，反推 `var` 在实践中的**实际**判据（约 30 次调用）。
2. 据此写判定 prompt，在 `relink.py` 那套 8 正 8 负标定集上迭代（每轮 16 对 × 2 模型 = 32 次）。
3. **放行门槛**：正例 confirm ≥6/8 且负例拒绝 ≥7/8。达不到就说明「同家族」无法自动判定，
   B 止步于第 1 步，第 3 步取消。

标定集要换成**留出集**（另抽 8 正 8 负，seed 不同），避免在迭代里过拟合那 16 对。

## 已定的结构（2026-10-15 用户确认）

**模式文件 + 条目 `pattern` 字段**：

```yaml
# catalog/patterns/PAT-0113.yaml
id: PAT-0113
title: <按成员集生成，不借用代表条目的标题>
shared_mechanism: <按成员集生成>
representative: INF-0958        # 树里入度最高者，并列取编号最小
members: [INF-0958, INF-0960, INF-0962, ...]

# catalog/entries/INF-0960.yaml
pattern: PAT-0113               # 新增
relations: [{kind: var, target: INF-0958}]   # 保持不变
```

模式与 var 关系**并存**：`relations` 仍是作者的逐条断言，`pattern` 是它所属的族。
`pattern` 由模式文件的 `members` 派生，`validate` 校验双向一致。

实测 `cause.objects` 多于一个的条目只有 **21** 条，而其中 20 条是「一个机制牵涉几个部件」，
不是「几个故障挤在一条」——最常见的是**缺陷 + 它的 golden/测试也同错**

### 过程中发现并修掉的两个自造 bug

1. **模式编号必须带编目命名空间**。两个编目各自分配了 `PAT-0035`，而 RAG 合并索引两库，
   于是 `--pattern PAT-0035` 把训练库的 `TRN-0135`/`TRN-0136` 也带了回来。改成
   `PAT-INF-0035` / `PAT-TRN-0012`；因为 `pattern-sync` 按成员重叠匹配而非按编号，
   重命名后 sync 是 no-op。这是 `AGENTS.md` 早就记过的 slug 同名问题的翻版。
2. **写手自报 `coherent: false` 会被静默采用**。`passed()` 原先只看复核票，而写手标 false
   时它只是概括了最大公因——复核可能照样放行那个标题，等于把不自洽的族当成模式。
   已改为 `coherent is False` 直接不通过，归入待复核。
